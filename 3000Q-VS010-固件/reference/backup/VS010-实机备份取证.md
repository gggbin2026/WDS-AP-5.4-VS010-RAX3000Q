# VS010 实机 NAND 备份 · 取证与 r24 修复依据

> 采集对象：`reference/backup/VS010-flash-backup-20240414-135754.tar.gz`（789,744 B）
> 15 个分区 + `proc-mtd.txt` / `manifest.txt` / `uname.txt` / `openwrt-release.txt`
> **sha256 与 manifest 15/15 全部匹配**，数据可信。
> 复现：`python3 sourcebuild/tools/parse-vs010-backup.py`
> 机器可读结果：`reference/backup/VS010-备份解析.json`

⚠ 包内时间戳 `20240414-135754` 是路由器**未同步 NTP 的本地时间**；
固件实际是 `Linux Nwrt 5.4.213 #0 SMP PREEMPT Sun Apr 14 05:49:22 2024`（`OpenWrt 19.07-SNAPSHOT / R23.4.16 / ipq50xx_32 / arm_cortex-a7_neon-vfpv4`）。
**采集动作发生在 2026-11-27**，这个日期别当成固件版本。

## 1. U-Boot：三方 godsun 版（不是原厂）

`mtd11-0_APPSBL.bin` 是 **32-bit ARM ELF**（`7f 45 4c 46` / machine 40），
从里面直接读到版本串：

```
U-Boot 2016.01-3e89586-godsun (2026-08-14 22:56:00 +0800)
arm-openwrt-linux-gcc (OpenWrt GCC 5.2.0 6404588+r49254) 5.2.0
```

内置能力（strings 实证）：`/uboot.html` web failsafe、`uboot_version` JSON、
`U-Boot Telnet Console`、`failsafe_write_uboot`、`bootipq`、`IPQ5018#` 提示符、
`smem ram ptable found`、NAND/QPIC 驱动、`qcom,ipq5018-pcie`。

🔴 **边界钉死**：按键采样 / web 恢复 / boot 分区选择**在 U-Boot 层**。
源码编译线改的是**内核 DTS 的 `gpio-keys` / `leds`**，改错最多按钮灯不灵，
**不会硬砖**。恩山那个变砖案例是刷了 3000Q 的 U-Boot —— **U-Boot 本体别动**。

**单槽启动**：`mtd12-0_APPSBL_1.bin`（1.25 MiB）与 `mtd09-0_CDT_1.bin` **全 `0xFF`**，
备用槽是空的。救砖只能走 web failsafe / Telnet / TTL，**没有第二份 U-Boot 可切**。
首次刷源码线建议 TTL 在手边。

## 2. U-Boot env：原厂变量保留，但 🔴 bootargs 不完整

`mtd10-0_APPSBLENV.bin` 前 4 字节 CRC，之后是 `\0` 分隔的 `key=value`：

| key | 值 |
|---|---|
| `SSID1` / `SSID5` | `ChinaUnicom-A081` / `ChinaUnicom-A081-5G` |
| `bootargs` | **`console=ttyMSM0,115200n8`** |
| `bootcmd` | `bootipq` |
| `bootdelay` | `3` |
| `baudrate` | `115200` |
| `machid` | `8040000` |
| `flash_type` | `11` |
| `fdt_high` | `0x4A400000` |
| `ipaddr` / `serverip` / `netmask` | `192.168.1.1` / `192.168.1.2` / `255.255.255.0` |
| `ethaddr` / `eth1addr` | `94:c9:b7:e5:a0:8x`（⚠ 本机 MAC，公开仓库已脱敏提示） |
| `sn` / `cmiit` / `soc_hw_version` | 原厂出厂信息 |
| `stdin/stdout/stderr` | `serial@78AF000` |

🔴 **这就是 r24 最关键的实证结论**：

> U-Boot env 的 `bootargs` **只有 console**，**没有** `ubi.mtd=rootfs` / `swiotlb=1`。
> 而好固件的 `/proc/cmdline` 里有这两个参数 →
> **它们只能来自内核 DTS 的 `bootargs-append`**，不是 U-Boot 追加的。

**修法**：`sourcebuild/target/ipq50xx/ipq5000-vs010.dts` 的
`bootargs-append = " ubi.mtd=rootfs root=/dev/ubiblock0_1 swiotlb=1 coherent_pool=2M"`
是**必须保留**的；`tools/verify.sh` 已加硬断言（删了直接 FAIL），
workflow 编译前也会复核备份 JSON 里 `env.bootargs` 不含 `ubi.mtd`。
删掉它 = UBI 不挂 rootfs = 开机起不来，不是「无线坏」那么简单。

## 3. MIBIB：16 分区（不是原厂 24）

详见 `VS010-MIBIB-分区表.md`。要点：表头 magic `0x55ee73aa/0xe35ebddb`、
version 4、`numparts=16`、条目 28 B、off/size 以 **128 KiB 块**为单位；
`rootfs @0x00900000 size 0x06e00000 (110 MiB)` = 大分区 U-Boot。
与 `/proc/mtd` 的 mtd0..mtd14 逐项吻合，前 15 项合计 9 MiB。

## 4. CDT：DDR 参数表，**不是** wifi board-id 的来源

`mtd08-0_CDT.bin`：`CDT\0` magic、version `2`、`RDD` 段 @`0x24`，
后面是一串 4 字节大端 DDR 时序值（`0x00000006 / 0x0000000e / 0x71 02 00 d0 …`）。
`mtd09-0_CDT_1.bin` 全 `0xFF`（空的）。

**如实结论**：在 CDT 前 4 KiB 里**没有** wifi board-id 字段（搜过 0x10/0x24/0x60 与 16/36/96，
命中的都是 DDR 参数里的数值，不是编号定义）。
所以 r22 那个悬案 —— 原厂 dtb 的 `qcom,board_id=0x10/0x60` 与 ath11k 容器
`qmi-board-id=36/96` 为何不同 —— **CDT 裁决不了**。
这两套是**不同软件栈各自的编号**，不是同一个寄存器。

**决策**：r24 继续用 kkstone 已验证的 84 B 容器头（`qmi-board-id=36` / `96`），
备选 `id=16` 留在 `sourcebuild/reference/variants/` 供实机试，不靠猜强行改主容器。

## 5. ART：与仓库既有文件 **100% 一致**，BDF 直接由它生成

`mtd13-0_ART.bin`（1 MiB，sha256 `e97b8f7a5190171d…`）：

| 仓库既有文件 | 与备份一致率 |
|---|---|
| `3000Q-VS010-固件/VS010-smem_0-ART.bin` | **100.00%** |
| `…/ATR文件/d83dcc685b5a-VS010-smem_0-ART.bin` | 99.85% |
| `…/ATR文件/RAX3000Q-mtd13-0ART` | 99.64%（3000Q 的，供对照） |

→ **之前 r22/r23 用的 ART 本来就是这台机器**，不需要再「换成本机专属」。

BDF 区段（QSDK 5.4 实机 dmesg 也证实 `bdwlan.b10` / `qcn6122/bdwlan.b60` 各 131072 B）：

| 频段 | ART 偏移 | 长度 | head | sha256 |
|---|---|---|---|---|
| 2.4G `ipq5018` | `0x1000` | 131072 | `01 00 04 04 00 00 00 00 00 80 f6 32 …` | `e7795d7e…` |
| 5G `qcn6122` | `0x26800` | 131072 | `01 00 04 04 00 00 00 00 00 80 65 51 …` | `5585d4f8…` |

🔴 **r24 实质修复**：r22 用的是 `whmzsu/vs010-openwrt` 拉来的通用 BDF
（与本机 ART 相似 99.20% / 97.70%）。r24 **直接从备份 ART 提取这两段**
生成 `package/ipq-wifi/board-cucc_vs010.ipq5018 / .qcn6122` 的 body，
**100% 本机校准**；84 B 容器头与 `qmi-board-id=36/96` 原样不动，
Q6 固件 / DTS / 驱动索引链路零改动。`tools/verify.sh` 会哈希断言 body == ART 段。

## 6. TRAINING / 其它分区

- `mtd14-0_TRAINING.bin`：512 KiB，内容以 `0x0f` 填充为主（NAND 训练数据），
  每台唯一，救砖/换 U-Boot 必需，**不进固件**
- `mtd00-0_SBL1.bin`：高通签名 MBN（含 `SecTools Test Attestation CA` 证书链，2021 签发）
- `BOOTCONFIG` 与 `BOOTCONFIG1` sha256 相同（双份同内容）
- `QSEE` / `QSEE_1`、`DEVCFG` / `DEVCFG_1` 内容不同，主槽为准
- 🔴 `0:ART` / `0:APPSBLENV` 含本机 MAC，仓库公开时建议脱敏；
  BDF 提的是 `0x1000 / 0x26800` 的校准段，**不含 MAC 字段**

## 7. r24 因此改了什么（逐条对应）

| 发现 | 修复 |
|---|---|
| env.bootargs 无 `ubi.mtd` | DTS `bootargs-append` 硬断言不可删（verify + workflow 双保险） |
| MIBIB 16 分区 / rootfs 110 MiB | 文档更正 r23「原厂 24 分区」推断；分区表逐字节留档 |
| ART 与仓库文件 100% 一致、BDF 就在 ART 里 | BDF body 改从 ART 提取，本机校准 100% |
| U-Boot = godsun 2026-08-14、单槽 | 边界钉死：内核 DTS 可改、U-Boot 不动；救砖路径写明 |
| CDT 无 wifi board-id | 不再靠 CDT 猜 16 vs 36，备选容器保留但不抢主包 |
| 线上两条 workflow 同名冲突（用户截图） | r24 过渡：源码线隔离到 `sourcebuild/` 双线并存；**r25 定型：融合线整体移除，只留 `build-source.yml`** |

## 8.  Privacy / 边界

- 备份包已归档在仓库 `reference/backup/`，**逐字节未改**
- `0:ART`、`0:APPSBLENV` 含 MAC / 序列号，公开仓库请自行脱敏
- 本文件所有数字来自二进制解析，**不是推断**；解析脚本可复跑
- 没跑真实 `make`，没有实机刷入源码线固件；`iw dev` 出双频接口仍需刷完亲眼确认
- 010 的融合线（官方 5.4.213 闭源栈）继续保留作保底，两条线互不干扰
